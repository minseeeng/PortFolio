# 온라인 장기 (C++ · WinSock select · Direct2D)

> 서버와 클라이언트를 혼자 설계하고 만드는 2인 대전 장기입니다. **진행 중**인 프로젝트입니다.
> 기획 결정(방 규칙, 실패 처리), 패킷 설계, 서버, 클라이언트 UI를 모두 직접 정하고 구현합니다.

| | 서버 `BoardGame_Server/` | 클라이언트 `BoardGame_Client/` |
|---|---|---|
| 기술 | C++, WinSock `select` | C++, Win32, Direct2D, DirectWrite, WIC |
| 핵심 클래스 | `Server`(접속·브로드캐스트) · `ClientContext`(세션) · `CRoom`(방) | `SceneManager` · `Scene`(닉네임 / 로비 / 게임) · `CNetCore` / `CNetClient` · `ResourceManager` · `CButton` · `CInputBox` |

> 리소스 이미지(`Resource/`)는 저작권 문제로 저장소에 넣지 않았습니다.

---

## 1. 일을 나눈 방식

목표를 5단계로 나누고 37개 태스크로 다시 쪼갰습니다. 각 태스크에는 네트워크(N)와 UI(U) 중 무엇이 바뀌는지 표시했습니다.

| 단계 | 태스크 | 상태 |
|---|---|---|
| 1. 닉네임 | 접속, 입력 전달(Window → App → Scene), 입력칸, 버튼, 실패 응답 | ✅ |
| 2. 로비 | 로비 패킷 설계, 유저 목록, 입장·퇴장 알림, 로비 채팅 | ✅ |
| 3. 방 | 방 설계, 방 목록, 방 만들기 → 게임 씬 전환 ✅ / 방 입장 · 나가기 · 게임 시작 | 🔶 |
| 4. 장기 | 판 좌표 ↔ 픽셀, 말별 규칙(그리기와 분리해 서버에서 재사용), 장군·승패, 이동 패킷 | ⬜ |
| 5. 예외 처리 | 게임 중 끊김, 닉네임 중복, 잘못된 패킷, 송신 길이 초과 | ⬜ |

- **핵심 경로**를 먼저 정했습니다: 방 입장 → 나가기 → 게임 시작 → 장기 규칙 → 네트워크 대전 → 끊김 처리.
- 일정이 밀리면 **자를 순서**도 미리 정했습니다: 로비 꾸미기 → 관전 → … (구조와 네트워크 핵심은 자르지 않음)

## 2. 패킷 설계

헤더 4바이트 + 페이로드, 패킷 최대 255바이트(`BUF_SIZE`). 서버와 클라이언트의 `PacketType.h`를 똑같이 맞춰 두고 시작합니다.

| 번호 | 타입 | 방향 | 페이로드 |
|---|---|---|---|
| 1 | `TYPE_NICK` | 양쪽 | 닉네임 (답장 = 확정 닉네임) |
| 2 | `TYPE_NICK_FAIL` | 서버 → 클라 | 실패 문구 |
| 3 | `TYPE_CHAT_SEND` | 클라 → 서버 | 채팅 내용 |
| 4 | `TYPE_CHAT_RECV` | 서버 → 로비 | `[닉네임 21][내용]` |
| 5 | `TYPE_ENTRY_LOBBY` | 서버 → 로비 | 닉네임 |
| 6 | `TYPE_EXIT_LOBBY` | 서버 → 로비 | `[닉네임 21]` |
| 11 | `TYPE_ROOM_CREATE` | 클라 → 서버 | 없음 |
| 12 | `TYPE_ROOM_ADD` | 서버 → 로비 | `[방장 닉네임 21][방 번호 2]` |
| 13 | `TYPE_ROOM_REMOVE` | 서버 → 로비 | `[닉네임 21][방 번호 2]` |
| 14 | `TYPE_ROOM_ENTER` | 클라 → 서버 | 방 번호 2 |
| 15 / 16 | `TYPE_ROOM_ENTER_OK` / `_FAIL` | 서버 → 클라 | 없음 |

**설계하면서 정한 것**
- **채팅 길이** = 100글자. `100 × 2 + 1 = 201바이트 ≤ 255 − 헤더 4 − 닉네임 21`로 계산해 한 패킷에 들어가게 함
- **채팅 닉네임은 서버가 붙임** → 클라이언트가 다른 사람 이름으로 채팅할 수 없음
- **유저 목록은 한 명씩 여러 번** 보냄 → 버퍼 크기를 늘리지 않고, 처음 목록과 새 입장을 같은 타입으로 처리
- **방장이 나가면** 남은 사람에게 자동으로 넘김. 0명이면 `ROOM_REMOVE`로 로비에 알리고 방 칸을 재사용

## 3. 클라이언트 구조

- **씬 구조**: `SceneManager`가 씬을 바꾸고, 씬 전환은 업데이트 전 한 곳에서만 일어납니다.
- **입력 경로**: `Window` → `App` → `Scene`. 마우스 이동은 마지막 칸을 덮어쓰고, 누름과 뗌은 보존합니다.
- **버튼**: 사실 2개(`inside`, `pressing`)로 상태를 계산합니다. 클릭은 "안에서 누르고 안에서 뗌"으로 판정하고, 밖에서 떼면 취소합니다.
- **리소스**: `ResourceManager::GetSprite(bmp, spr)`로 같은 그림은 한 번만 로드하고 버튼은 빌려 씁니다. 반납은 게임 끝에 한꺼번에 합니다.
- **네트워크**: `CNetCore`(소켓)와 `CNetClient`(패킷 조립)를 나눴습니다. Enter를 누른 순간 바로 send합니다.

## 4. 막혔던 지점 (증상 → 원인 → 해결)

| 증상 | 원인 | 해결 |
|---|---|---|
| 버튼이 항상 눌린 상태로 판정 | 출력 enum(`BUTTON_STATE`)과 입력 enum(`MOUSE_TYPE`)을 섞어 `&& BUTTON_PRESSED`가 항상 참 | 입력과 출력 상태를 분리 |
| 방 추가 패킷이 아닌데도 방 목록이 늘어남 | `else if (TYPE_ROOM_ADD)`, `type ==` 누락으로 항상 참 | 비교식 수정, `if` 줄줄이 → `switch`로 정리 예정 |
| 퇴장한 유저를 목록에서 못 지움 | `wcscmp` 자리에 `wcscpy_s` → 빌드는 통과하고 비교 대신 덮어씀 | 비교 함수로 교체 |
| 창 밖에서 마우스를 떼면 버튼이 눌린 채 남음 | `SetCapture` 없음 → 창 밖의 `WM_LBUTTONUP`이 안 옴 | 알려진 이슈로 기록 |

## 5. 스스로 짚어 둔 다음 과제

AI 코드 리뷰와 직접 점검으로 찾은 구조 문제를 정리하고, 언제 고칠지 정해 두었습니다.

- **서버 역할 나누기**: `ClientContext::ProcessPacket`에 닉네임, 채팅, 방 규칙이 모두 들어 있음 → 장기 규칙이 붙기 전에 네트워크(`Server`)와 규칙(로비 / 방)으로 분리
- **`Send` 하나로**: `strlen`을 쓰는 쪽과 바이트를 그대로 보내는 쪽 두 갈래 → `Send(type, data, len)`
- **잘못된 패킷 처리**: "아직 덜 옴"과 "망가진 패킷"이 둘 다 `false` → 망가지면 수신 버퍼가 영원히 막힘
- **주소 고정**: `127.0.0.1` → PC 두 대 시연을 위해 `INADDR_ANY` + 클라이언트 IP 입력
